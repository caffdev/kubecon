Start with the cluster admins. What do the people with three hundred clusters do? Not that. On the left is the row from two slides ago: fifty-four steps for one cluster, by hand. Nobody presenting at this scale does that any more. What they do instead is on the right: the upgrade is a change to one field, a version number, in a pull request. It gets reviewed, it gets merged, and a controller does the fifty-four steps, the same way every time. Two routes for us. On-prem, that's Cluster API. And to be straight about it: Cluster API still uses kubeadm underneath. kubeadm isn't going anywhere. What goes is someone running it node by node. The clusters become a fleet, managed from code. Cluster API replaces machines one at a time instead of patching them in place. The tool stays; the hands go. In AWS, it's EKS Auto Mode. AWS upgrades the control plane, then replaces the nodes for us, and it runs Karpenter itself, which takes one tool off our list. The evidence, in the square on the left. Meta runs about a hundred clusters for AI research and inference with about fifteen engineers. LinkedIn runs three hundred clusters and around three hundred thousand nodes; with skip-level upgrades they took three minor versions from six fleet-wide waves down to one. NVIDIA converged about fifty-six hundred nodes in thirty minutes. Small teams run big fleets, because nobody touches a cluster by hand. On-prem, that's the cluster admins' answer: the hands leave the upgrade. In AWS we can go further.
