“Sandbox Your Agents” keynote (Red Hat); Groundhog Pod: Kata pod snapshots (Microsoft); Agent Sandboxes on Kubernetes (Google). Nitro Sandbox: EKS user guide (Auto Mode; Kubernetes 1.36+). One line per pod picks it: runtimeClassName.

Every one of those agents runs code, and often it's code the agent just wrote. So the question is what's between it and the node. Follow the arrows. Each one is the agent's system calls, and where it lands is the whole story. On the left, a plain container: its calls go straight to the node's kernel, the one every other pod shares. A namespace, not a wall. That's fine for code a person reviewed. It isn't a cage for code an agent wrote thirty seconds ago. That was a keynote at the show: sandbox your agents. In the middle, gVisor: a kernel written in user space answers the calls itself, so most kernel exploits stop there. It starts fast. But it needs a node image we build, and Auto Mode picks its own images, so gVisor is for node groups we run ourselves. On the right, a microVM: every pod gets its own small virtual machine with its own kernel. If something escapes, it lands in a VM, not on the node. In open source that's Kata, and Microsoft showed how pod snapshots take most of its start-up cost away. On EKS Auto Mode it's built in: AWS calls it Nitro Sandbox, Firecracker microVMs, with no setup. That's our default for agents. These aren't layers. They're three choices, made per pod, with one line in the spec: the runtime class. That's agents as workloads. Now agents as users: caged, an agent still has to do things, and it does them through tools.
