Every one of those agents runs code, and often it's code the agent just wrote. So the question is what's around it. A container shares the host's kernel with every other pod on the node. It's a namespace, not a wall. That's fine for code a person reviewed. It isn't a cage for code an agent wrote thirty seconds ago. That was a keynote at the show: sandbox your agents. The next shell is gVisor: a kernel written in user space that answers the agent's system calls itself, so most kernel exploits stop there. It starts fast, with some overhead on system calls. That's our default for agents. The outer shell is Kata: every pod gets its own small virtual machine with its own kernel. If something escapes, it lands in a VM, not on the node. It starts slower, and Microsoft showed how pod snapshots take most of that cost away. That's for untrusted code and for tools that run anything they're handed. And picking one is one line in the pod spec: a runtime class. Caged, it still has to do things, and it does them through tools.
