Order: LinkedIn’s canary pipeline (staging, canaries in parallel, then prod cluster by cluster).

Twenty platform apps, rolled out the way we roll out any app: progressively. Read the picture from the left. The middle of the ripple is the test cluster. The next ring is one canary cluster: real workloads, real traffic, but just one. Then the prod fleet in waves: wave one, wave two, and the rest of prod. A new version of a platform tool, say a new Argo CD, starts in the middle and moves outward one ring at a time. How. One definition per tool, an ApplicationSet, and progressive sync takes it one wave at a time. Which wave a cluster is in is a label on the cluster, not a list in a pipeline, so when cluster twenty-nine shows up it just gets a label and it's in. And one train we can get off entirely. On EKS Auto Mode clusters, the outlined ones, AWS runs Karpenter itself. The cheapest rollout is the one somebody else does. LinkedIn rolls their cluster services out in this order: staging first, canaries in parallel, then prod one cluster at a time. But a ring only moves outward when the tool proves itself.
