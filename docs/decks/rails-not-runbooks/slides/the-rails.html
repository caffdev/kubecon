Here's the turn. On rails, a rollout stops being a procedure and becomes three objects. One: a change is one field. On the left, a pull request that moves payments to a new image digest. It's the same shape for a cluster's Kubernetes version in a Cluster API object, or a platform tool's release. One line in Git, reviewed like any other. Click. Two: a wave is a label. Every cluster carries a wave label: test, canary or prod. One ApplicationSet with a RollingSync strategy rolls the change to the test cluster, then the canaries, then prod a quarter at a time, and only inside the change window, Monday to Thursday, nine to five. That window is a syncWindows block in the Argo CD project, not a calendar invite. Click. Three: a gate is a Job. After each sync, a PostSync hook runs our check: targets up, rule errors zero, for fifteen minutes. Exit zero, and the next wave starts. Exit one, and the sync fails and the wave stops before prod. Argo CD doesn't roll back by itself; the revert is one commit, and a bot can open it. Click. So nobody clicks sync. Teams hold on to manual sync because today it's their only change control. The window, the gate and a policy test in CI give them that control back. In our illustrative model, sixteen hundred hand rollouts become about eighty wave approvals a year. One catch: progressive sync sits behind a controller flag in Argo CD, so we check it on a test ApplicationSet before we lean on it. That's the shape.
