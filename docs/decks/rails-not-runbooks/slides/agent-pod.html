Workloads first. Here's one agent as Kubernetes sees it: a Job. Jenkins, an alert or a schedule creates it, it does one task, and it's gone. Five fields matter. runtimeClassName isolated-sandbox: in EKS Auto Mode that's Nitro Sandbox, built in. The pod runs in its own Firecracker microVM, so the code the agent just wrote never touches the node's kernel. No extra setup; AWS documents it as the simplest way to run isolated pods. serviceAccountName: wired to Pod Identity, so it gets a short-lived role. No keys in the image. automountServiceAccountToken false: no Kubernetes API token just because it's a pod. activeDeadlineSeconds: killed at fifteen minutes, whatever it's doing; ttlSecondsAfterFinished cleans it up, and its logs are already in the lake. nodeSelector and tolerations: agents run on their own tainted node pool, grown for a burst and emptied after. Nobody approves each agent; the spec is the approval. Podium runs this shape: every coding agent an isolated pod. The catches, from the EKS user guide: existing Auto Mode clusters need Kubernetes 1.36 for sandbox pods, and there's no GPU passthrough yet. On-prem, the same line names gVisor or Kata instead. runtimeClassName is the line that matters, because a container is not a cage.
