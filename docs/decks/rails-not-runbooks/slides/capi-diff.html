and Cluster API does the 54 steps.

On bare metal, “replace a machine” means re-provisioning it: Metal3, or vSphere / Nutanix if ny4 runs on VMs. Choosing the provider comes first.

So here's the admins' fix, on-prem. kubeadm stays. The hands go. On the left is the whole upgrade, as a pull request. It's a Cluster API Cluster object for ny4, built from a ClusterClass we'd call onprem-kubeadm. Three control-plane machines, six workers. The upgrade is one line: version, v1.36 to v1.37. That's the diff someone reviews. The versions are illustrative. On the right, top: what that used to be. Fifty-four hand steps for this one cluster. Click. Bottom: what Cluster API does with the one line. The control plane first, one machine at a time: a new machine at the new version joins, the old one is drained and deleted. Then the workers, the same way, one extra machine at a time. It's still kubeadm underneath. Nobody types it. The catch, and it's the first thing an admin will ask: replacing a machine on bare metal means re-provisioning a physical server. That's what Metal3 does. If ny4 runs on VMs, it's the vSphere or Nutanix provider instead. Picking that provider is the first decision, before any of this works. One field per cluster.
