And the freeze becomes something the cluster enforces. Today "nothing goes out during the freeze" means someone refusing to click. The change record gets approved in the ITSM system, exactly as it is today. We project the approved record into the cluster as a custom resource. Policy reads that resource at admission. The decision worth defending is that admission never calls the ITSM API at request time. Admission is a hot path, and a policy that calls an external service fails closed the first time that service is slow. The free half: Argo CD's own sync windows already handle the calendar freeze. Use them for that, and keep policy for "this specific change needs a record". Only then does prod auto-sync go on. It's the last item in stage B, on purpose. This and the auto-sync work are one conversation, not two. Present them in sequence and someone funds auto-sync and defers the gating. After B, promotion and the fleet.
