Percentage ramps assume requests are interchangeable, divisible and single-component.

Not interchangeable

A random slice of users' critical jobs lands on a version nobody validated.

Not balanced

A percentage can't balance job types; some types miss the ramp window entirely.

Not divisible

An all-or-nothing change, like a schema migration, can't apply to a share of requests.

Not pinnable

In a multi-component change, one request hits one new and one old component.

LinkedIn, canary namespaces for cluster-critical services, KubeCon NA 2026

This is LinkedIn's articulation, and it's the best one we heard. Percentage ramps quietly assume three things about requests. That they're interchangeable: but a random ten percent means some users' critical jobs land on a version nobody validated. That they're balanced: but a percentage can't balance job types, and some types miss the ramp window entirely. That the change is divisible: but a schema migration is all or nothing. And that it's one component: but in a multi-component change, one request hits the new version of one service and the old version of the next. This is why our canary answer is per workload class rather than one pattern for everything. If we're running long, this slide is the one to cut. LinkedIn's answer for those cases needs no mesh at all.
