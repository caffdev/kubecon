Without this one, a GitOps config change reports success while the running pods keep serving the old value. That falsifies "Git is the state of the world" on the very day we say it. Three places a config value can live, and they aren't interchangeable. A ConfigMap or Secret in our Git repo: Reloader rolls the deployments that use it, so it's commit, sync, roll. Good. The middle row is the trap. When the value lives in Config Server's own backing config, Reloader rolls the config server, and its clients keep the cached value. And client-side refresh scope, with an actuator refresh per instance, is out of band: Git no longer describes what's running. Our lean, and this is ours, not from the show, and untested: make the roll the refresh mechanism. It needs one Spring-owning team to confirm which beans tolerate a restart. And it opens a question worth asking in the room: does any app's config genuinely need in-place refresh? If not, the config-server refresh path can retire, which is a simplification we'd get for free. Stage B is the one that buys the trade.
