Classic and AI workloads share one OTel layer, and agents only read its lake.

A lake is a snapshot. A gate mid-rollout still reads live metrics through one narrow tool.

It's the layer that sees both kinds of workload. This usually gets framed as OTel beating Prometheus. It isn't. Prometheus stays, top right, as a place metrics land. OTel is the layer in the middle. On the left, classic workloads: services and batch jobs, with metrics, logs and traces. Below them, AI workloads: model servers and agents, with things classic tools have no words for: tokens, tool calls, which model answered, what it cost. IBM and JPMorgan showed inference servers that emit OTel traces and get scraped by Prometheus, both at once. Both go through the same collector on every cluster. That's the Splunk OTel collector we already run, so it isn't a new tool, and it stamps the same cluster, namespace and team on everything. And it all lands in one lake. The agents sit on the shore and read: is this alert real, did this canary get worse, which hour is quiet enough to upgrade. There's no path from the shore back to production. Read-only is what lets us say yes to agents analysing prod without handing them prod credentials. The honest limit, bottom left. Mastercard argued the other side: a lake is a snapshot, and a stale index can mislead a model. They're right for live decisions, so a gate in the middle of a rollout reads live metrics through one narrow tool. The lake is for triage and trends. So here's the same person, with the same fleet.
