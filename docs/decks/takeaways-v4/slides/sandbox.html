Our default in AWS

EKS user guide: Auto Mode “includes Nitro Sandbox support with no additional configuration” (Firecracker; Kubernetes 1.36+). “Sandbox Your Agents” keynote (Red Hat). Microsoft, Groundhog Pod: Kata VM snapshots. AWS, Agent Sandbox on EKS (no deck).

A container is not a cage. Here's why, as three syscall paths. These are alternatives, not layers: one runtime class per pod. On the left, a plain container. The agent's system calls go straight to the host kernel every pod on that node shares. A namespace, not a wall. Fine for code a person reviewed; not for code an agent wrote a minute ago. Click. gVisor. The calls go to the Sentry, a kernel in user space, and only a narrow set reaches the host. Fast to start; syscall-heavy work pays. It needs our own node image, so it's for on-prem, not Auto Mode. Our on-prem default. Click. A microVM. Each pod gets its own guest kernel behind a hypervisor, so an escape lands in a VM. On-prem that's Kata on our own KVM hosts; Microsoft showed snapshots taking away most of the start-up cost. In AWS it's already done for us: Auto Mode includes Nitro Sandbox, a Firecracker microVM per pod, selected with runtimeClassName isolated-sandbox, no setup. That's our default in AWS. The catches: Kubernetes 1.36 or later, and no GPU passthrough yet. AWS's own talk said it simply: a runtime class on a normal pod spec. That's agents as workloads. As users, they work through tools.
