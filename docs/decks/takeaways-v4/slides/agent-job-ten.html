Workloads and users first, because they're the same object. To Kubernetes, an agent is a Job: Jenkins, an alert or a schedule creates it, it does one task, and it's gone. Three lines are the fence. One, runtimeClassName isolated-sandbox. A container shares the node's kernel; this gives the agent its own. In EKS Auto Mode that's Nitro Sandbox, a Firecracker microVM per pod, built in. On our own hardware the same line names gVisor or Kata. Two, the service account, wired to Pod Identity. When the agent acts as a user, it carries a role that expires. Passwords stay behind a gateway and never enter the agent; for tools over MCP, that gateway is where a Cedar policy decides who may call what. Three, a deadline: fifteen minutes, then it's killed and cleaned up. Nobody approves each agent; the spec is the approval. Click. And when it changes something, it meets the same rule as everyone: one CEL admission policy, images from our registry, by digest. It never mentions people or agents, so the reply is the same for all three. Write rules against the action, not the actor. The catch, from the EKS user guide: Kubernetes 1.36 on existing Auto Mode clusters, and no GPU passthrough yet. So, fenced in, what's its first job? Not fixing anything. Explaining.
