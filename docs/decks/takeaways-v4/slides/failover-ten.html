Remember "fingers crossed for AWS". This is what replaces it, and it's where the engineering is. Four layers across two AWS regions, and the second cloud on the right. Start with delivery: placement is labels, region in aws-1 or aws-2, so the app already runs in both regions, three replicas each. Nothing gets deployed during an outage. Click. Region one goes down. Detection starts the clock: health checks have to fail enough times to be believed. Click. Traffic moves: Global Accelerator at the edge, Route 53 behind it, Istio locality failover inside. All of it lands on region two. Nobody redeployed anything. Click. Capacity. Region two was sized for half the traffic and just got all of it. The autoscaler doubles the pods and Auto Mode adds nodes: launch, image pull, warm-up. Minutes, and part of our recovery time whether we budget for it or not. Click. State. Region two's database replica is promoted to writer. The slowest layer, and not a Kubernetes problem at all. So recovery time is a sum, and the data sets it. No seconds on the slide on purpose: we measure each one at a game day. And if all of AWS goes, the second cloud is a warm standby; how data crosses clouds is still undecided, and the slide says so.
