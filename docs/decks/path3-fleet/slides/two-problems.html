Multi-cluster

That's fleet toil. Multi-cluster has a second problem that looks similar and isn't, and confusing the two is how you end up buying a scheduler for a traffic problem. Left branch: fleet toil. One definition, many clusters. The answers are ApplicationSets with progressive sync, rolling out in waves, Cluster API or Auto Mode for cluster lifecycle, and shipping the check with every change. Right branch: losing a region. Both regions already run the app, so placement isn't the problem. It's traffic, state and capacity: getting users to the surviving region, keeping data consistent, and having enough room there. Karmada is the real multi-cluster scheduler: placement, propagation, rescheduling. It's good, and Bloomberg runs it in production. But it sits on neither branch for us until we can name a workload that needs scheduling rather than placement. That's decision 2: which production workloads can't run active-active? If that list is empty, Karmada stays on the watch list and the decision closes. The region branch first, because customers see it.
