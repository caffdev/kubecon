EKS-VS-ECS.md §2

The question isn't "EKS or ECS". It's "EKS, or EKS plus ECS". We already run Kubernetes on-prem and EKS in two regions, and everything we committed to at KubeCon lands on Kubernetes. ECS wouldn't replace anything. It would be a third container platform. Across the top: deploy, policy, identity, observability, and the new one, agents operating it. On-prem and EKS share one API and one set of tools, which we're building anyway: Helm and Argo CD, CEL and Kyverno at admission and in CI, Pod Identity and IRSA, the OTel collector, and one API that every MCP tool already speaks. Add ECS and every column gets a second answer. Task definitions and their own pipelines. IAM and pipeline checks, with no admission point to enforce policy. Task roles, a second identity model to audit. FireLens and CloudWatch, a second set of dashboards. And a second API surface for every agent and MCP tool, which matters more every month, because the main consumer of the platform is becoming a machine, and machines are good at one well-documented API and worse at two. It's not "some workloads get simpler". It's two of everything, and on-call has to know both. And the old argument for ECS, that it's simpler, closed last year.
