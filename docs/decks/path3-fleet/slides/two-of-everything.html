EKS-VS-ECS.md §0, §2, §3

The question isn't "EKS or ECS". It's "EKS, or EKS plus ECS". We already run two container platforms: Kubernetes on-prem, and EKS in two regions. ECS wouldn't replace either of them. It would be the third. Across the top are the five jobs a platform does: deploy, policy, identity, observability, and the new one, agents operating it. Platforms one and two share one answer to each, the band you see, down to one API that every MCP tool already speaks. We're building that anyway. Click. Add ECS, and every column gets a second answer, and every one of those boxes is new work. Task definitions and their own pipelines. No admission point for policy. A second identity model to audit. A second set of dashboards. And a second API for every agent and tool, which matters more each month, because the main consumer of the platform is becoming a machine, and machines are good at one well-documented API and worse at two. Two of everything, and on-call has to know both. Click. The old argument for ECS was that it's simpler. That stopped being true in 2025. EKS Auto Mode went GA in December 2024, ECS Managed Instances in the autumn of 2025, and they're the same product shape: AWS runs and patches the nodes on both. When AWS cut GPU fees this July, it cut them on both, on the same day. What's left of the difference is the Kubernetes API, and for us that's the asset, not the cost. So we stay on EKS.
